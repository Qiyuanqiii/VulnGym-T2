## 已解决的具体漏放

旧 OpenClaw `entry-59467` 把工厂片段标成 supported 入口，理由又明确承认工厂到处理函数的调度没有直接读到、仅由命名推断。**新版本回放这条真实旧输出时，会把 EP 置为 uncertain，整体留为 draft，错误码 `supported_reason_conflict`。** 原理由、引用及建议位置保留；CO 原有字段不受连带删除。旧运行文件逐字节保持不变。

回放只使用已保存的公共回执文本核对位置，不读取目标仓库、不发送 HTTP。它是旧输出对新检查的回归验证，不是一次新的模型生成，也不是人工语义批准。现场 `replay_saved_candidate.py` 与 `replay-result.json` 可重复验证该结论。

## 实现与边界

- 新增 `support_consistency.py`，规则版本 `declared-support-v1`。只检查本字段当前 supported 理由中少数明确承认必要前提未建立的模式：外部入口角色、工厂调度按名字推断、所选操作的缺陷行为、选定版本上的所述行为，以及在 `affected_range_and_source` 下被自身否认的版本范围映射。
- 不是 `unknown/not read` 关键词黑名单。明确引用、假设、已纠正历史叙述不自动判错；入口已建立但部署配置未知不降级；`behavior_at_revision` 不因为没有官方版本范围映射而降级。只看字段自身理由，不从可选 trace 缺失向 EP/CO 传播。
- 命中时保留 `pre_check_status`（本检查前状态，不是原始 HTTP 判定）、原理由/引用和建议值，仅对应必需字段转为 uncertain；不增加 `annotation_errors` 或模型错误计数。机器一致性待审不等于 API/格式故障。
- 检查结果进入原有的一次自查，不新增模型轮次。初稿已发现矛盾时，自查仅改理由、desc 或引用顺序，不能清除待审。原始承认保留在 `support_consistency_hold` action 中。
- 改选位置、增加同 SHA 成功源码引用，或把过度声明的 range basis 缩为源码行为 basis，可以重新进入原检查；未读位置、无效字节仍被原检查挡住。这些变化只是重新检查的必要信号，不证明新增引用真的解决了语义问题。
- 规则和自查指引明确工厂/注册包装不单独证明外部回调；只把 trace 设空并不能补足 EP 自身的必要依据。提示版本变为 `snapshot-guidance-v2`，wire、正式 15 字段 entry 格式、请求与工具上限不变。
- 两种复核报告均显示冲突的字段、必要前提和规则；检查未命中只表示没有发现这组有限模式，**不表示通用语义一致、事实正确或已被导师认可**。改换措辞、未覆盖语言表达、错误引用的语义含义仍可能漏检，不宣称万能判定器。
