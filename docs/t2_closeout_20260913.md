## 交付接口与空值契约

使用现有 CLI 或本地 Web 工作台。公告正文、JSON、Markdown、HTML、patch/diff 文件、混合资料、URL 批次可进入同一处理流程；本地仓库须事先可用，程序不执行目标程序或自动 clone/fetch。直接 PDF/图片解读不在当前输入适配范围，先提供其文本。交互形式本身不替代输出质量。

- `entries.jsonl`：字段完整且通过结构、来源和源码位置检查的候选；15 个正式字段，`verify=0`。
- `drafts.jsonl`：每个未完整候选/输入失败占位各一行，相同的 15 个字段名。缺失标量和整个缺失位置用 `""`，数组用 `[]`，`verify=0`。不存在的位置不造 `{file,line,code}`。这是待复核输出，不宣称满足完整条目的非空 schema。
- `review.jsonl`：保留原字段状态、建议、出处、不确定原因、技术失败和原始 `null`；不把建议值偷偷填回草稿。
- `reports.jsonl` 只聚合完整条目；`summary.json` 分开输入、完整候选、草稿、输入失败及未处理数。`draft_export_count` 包含输入失败占位，`draft_count` 不包含。

## 验收看什么

| 要求 | 完成判据 / 不可偷换的边界 |
| --- | --- |
| 公告、patch、源码融合 | 有真实读工具记录；缺少某材料须明确说明，不把链接存在当作已读正文。 |
| 元数据、版本与位置 | ID/来源规范化，固定 origin/verify，真实 40 位 SHA，file/line/code 对应已读取的同版本代码；SHA 合法不等于受影响版本已确认。 |
| 结构自检和回改 | 预检反馈到自查，终检仍执行；正式条目及 reports 的关联一致。错误未修复则保留草稿，不能假报成功。 |
| 宁缺勿错 | 空值草稿及不确定原因可导出；区分合理未知、可改进的漏读、技术失败，不一律包装为保守正确。 |
| 批量 | 一个输入一份处理记录、完整/草稿分别保留，停止时显示未处理数；无自动 HTTP 重试。 |
| 智能体过程 | 分阶段规划读取、字段判读、结构成稿、自查；历史/目录/源码/搜索/diff 等多类工具实际参与。 |
| trace / 业务逻辑 | 有限源代码关系要能逐项说明；非空 trace 不代表全局权限/部署证明。没有固定操作模式的场景仍需公告与源码联合判断。 |
| T1 | 按本轮明确指示不实现；同模型自查不命名为独立 T1。 |
